# 주문·구매·메일 운영 계약

서버의 최근 주문 관제, 구매 실행, 고객 전달, 메일 상태 추적 변경을 공개 가능한
구조와 상태 계약으로만 정리한 문서다. 실제 주문번호, 상품명, 고객 정보, 외부
판매 채널명, 계정명, 주소, 키 원문, 메일 원문, 서버 경로와 인증 설정은 포함하지 않는다.

## 1. 주문 관제

주문 관제는 외부 주문 조회 결과를 업무 DB의 정본으로 적재하고, 조회 위치와 마지막
성공 시각을 함께 기록한다.

- 상품주문 식별자는 유일 제약으로 중복 적재를 막는다.
- polling 실행에는 임대 소유자와 만료 시각을 둬 동시에 한 번만 실행한다.
- 주문 고객의 이름·연락처·주소·이메일은 관제 정본에 저장하지 않는다.
- `NEW → QUEUED → OK/HOLD → DONE` 흐름과 취소 상태를 분리한다.
- 상태 변화, 판단, 재알림, 발송 기한 경고는 별도 사건 이력으로 남긴다.
- 조회 실패는 마지막 성공 시각과 오류를 보존하고, 다음 실행이 빠진 구간을 다시 확인한다.

## 2. 외부 계정 상태 관측

구매 실행에 사용하는 외부 계정은 별도 관측 기록으로 관리한다. 관측 결과는 참고
신호이며 구매의 선행조건이나 성공 증거로 취급하지 않는다.

- 정기 점검은 하루 횟수와 점검 간격을 제한한다.
- 로그인 유지, 로그아웃, 추가 인증 대기, 사람 확인, 계정 경고, 판단 불가를 구분한다.
- 인증번호나 사람 확인이 필요하면 자동 통과하지 않고 사용자에게 중단 상태를 보고한다.
- 계정 이름, 로그인 주소, 자격증명 이름과 값은 저장소·로그·Slack에 공개하지 않는다.

## 3. 구매 상태와 중복 방지

구매 기록은 주문 1건과 외부 구매 1건의 실행 상태를 연결한다.

```text
STARTED
   ├── PAID ── KEY_CAPTURED ── SENT
   │             └── KEY_PENDING
   ├── UNKNOWN
   └── STOPPED
```

- 이미 진행 중인 구매가 있으면 새 구매를 시작하지 않는다.
- 같은 주문에 살아 있는 구매 기록이 있으면 재결제하지 않고 기존 기록을 이어간다.
- 결제 완료, 키 확보, 결과 불명, 중단을 각각 별도 상태로 기록한다.
- 키 원문은 암호화 저장소에서만 다루고, 화면·로그·Slack·모델에는 끝 일부를 가린 값만 보낸다.
- 키 중복 판별용 해시와 보관 만료 시각을 기록한다.
- 보관 기간이 지나면 키·고객 주소 원문을 삭제하고 가림 값과 감사 메모만 남긴다.
- 키가 확보되지 않았거나 결제 결과가 불명확하면 다시 결제하지 않고 대조 단계로 멈춘다.

## 4. 인증코드 입력 경계

외부 메일함에서 인증코드를 확인하는 도구는 코드 원문을 호출자에게 반환하지 않는다.

1. 허용된 발신 조건과 최근 도착 시간을 확인한다.
2. 인증 관련 문맥에서 후보를 찾는다.
3. 후보가 정확히 하나일 때만 허용된 외부 화면의 입력 칸에 직접 넣는다.
4. 후보가 없거나 여러 개면 입력하지 않고 사용자가 원문을 확인하도록 중단한다.
5. 출력·로그·Slack·모델에는 도착 여부, 제목, 후보 개수와 입력 결과만 남긴다.

## 5. 고객 전달과 직접 전달 처리

키 전달은 구매 기록을 다시 확인한 뒤 배송 역할이 수행한다.

- 주문 상태와 클레임 상태를 API로 재확인한다.
- 수신 대상은 판매자 화면에서 확인하되 원문 주소를 AI 대화나 로그로 옮기지 않는다.
- 메일 발송이 성공한 뒤에만 직접 전달 상태를 요청한다.
- 이미 메일을 발송했거나 직접 전달을 완료한 기록은 중복 실행하지 않는다.
- 발송 결과, 외부 메시지 식별자, 직접 전달 결과를 업무 DB에 기록한다.
- 주소 변경, 재발송, 환불, 고객 CS 판단은 자동으로 확정하지 않는다.

## 6. 메일 상태와 수신 확인

보낸 메일 화면은 발송 기록과 전달 상태를 운영자가 확인하기 위한 화면이다.

- 전달 상태는 접수, 서버 전달, 반송, 발송 차단으로 구분한다.
- 외부 전달 로그를 주기적으로 대조해 가장 진행된 상태를 업무 DB에 반영한다.
- 수신 확인 픽셀은 열람 시각과 횟수만 기록한다. 외부 이미지 차단 때문에 미열람은
  미수신의 확정 증거가 아니다.
- 목록에는 수신자와 키를 가림 값으로만 표시한다.
- 원문 보기 기능은 관리자 권한·명시적 버튼·감사 기록·캐시 비활성화를 함께 요구한다.
- 공개 화면에서는 원문 키와 고객 메일 본문을 제공하지 않는다.

## 7. 자동화 연결

정기 작업은 고정된 작업 키와 역할별 문서 계약으로만 실행한다. 주문 polling,
계정 상태 점검, 메일 상태 대조, 보관 원문 정리는 서로 다른 작업으로 분리한다.

스케줄러와 알림 계층은 트리거와 보고를 담당하고, 주문·구매·메일 상태의 정본은
업무 DB에 둔다. 공개 저장소에는 작업 의미와 상태 경계만 기록하며, 실제 스케줄
설정·토큰·메일함·외부 계정·운영 데이터는 서버에 남긴다.

## 공개 범위

이 문서와 공개 프런트엔드는 다음만 보여 준다.

- 상태 모델, 중복 방지, 보존·삭제 원칙
- 가림 값 기반 메일 목록과 전달 상태 UI
- 역할별 도구 경계와 중단 조건

다음은 공개하지 않는다.

- 외부 판매 채널·공급처의 이름, URL, 계정과 가격
- 고객 이메일·주문 원문·결제정보·게임 키
- 메일 서버 주소, 내부 포트, 자격증명, API 토큰
- 운영 DB·메일함·브라우저 세션·로그·백업 원본
